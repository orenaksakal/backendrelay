# Disaster-recovery drills (P7.8)

This directory holds the operator kit for the full recovery drills: a real
backup restored into staging, the lifeboat on another provider, and one app
restored on its own. The procedures and the result table live in
[`docs/operations.md#disaster-recovery-drills`](../../docs/operations.md#disaster-recovery-drills);
this file adds the exact staging, lifeboat and recording details.

The abuse and isolation drill is a separate kit in [`abuse/`](abuse/README.md);
the failure drills live in [`../scale-local/`](../scale-local/drills.sh).

Nothing here needs a cloud account to read. The drills themselves do: run them
from the production host with the offline age identity available, never from a
laptop with production credentials copied onto it.

| File | Purpose |
| --- | --- |
| `record-drill.sh` | Append one measured drill to the local ledger and print the row for `docs/operations.md#disaster-recovery-drills`. |
| `lifeboat/fly.toml.example` | Fly.io Frankfurt template for the signed server digest. Replace every `REPLACE_WITH_*` placeholder. |
| `lifeboat/README.md` | Fly.io and Railway lifeboat setup, secret restore and teardown. |

## Before any drill

1. **Prove the backup first.** `recovery.py backup` writes a receipt only after
   the off-host checksum verifies. Read the newest receipt and refuse to drill on
   anything else:

   ```sh
   sudo ls -lt /var/lib/backendrelay/backups/*.receipt.json | head
   sudo jq -r '.offhostVerified, .completedAt, .bundle, .sha256' \
     /var/lib/backendrelay/backups/<stamp>.receipt.json
   sudo sha256sum /var/lib/backendrelay/backups/<stamp>.tar.age
   ```

   `pgbackrest info` may be used instead when the drill explicitly tests the
   physical repository. Do not mix a pgBackRest database with a `recovery.py`
   keyset copy without checking that they describe the same deployment.

2. **Choose a window.** Drill (a) and (c) touch staging only. Drill (b) creates a
   second production copy on another provider; if the drill is cut short, that
   copy is still a security and cost problem. Book enough time to tear it down.

3. **Keep secrets out of argv and shell history.** Read the database URL and
   dashboard token from a mode-0600 file or an exported variable. Do not paste
   keysets into a terminal, a ticket or a chat.

4. **Write down the start.** Use a UTC timestamp and seconds, not a feeling:

   ```sh
   date -u +%Y-%m-%dT%H:%M:%SZ
   date -u +%s
   ```

5. **Set the target before the run.** Record it in the drill notes. The target is
   an owner decision: for example a staging restore that has to fit a maintenance
   window, and a lifeboat that has to fit the time you are willing to be down.

## (a) Latest backup into staging

The full command sequence is in
[`docs/operations.md#a-restore-the-latest-backup-into-staging`](../../docs/operations.md#a-restore-the-latest-backup-into-staging).
Keep these points in mind:

- Use the staging compose project (`backendrelay-staging`, `aux-postgres`,
  `aux-db`). The production `postgres` service must never be stopped or have its
  volume replaced.
- `primary.dump` is a custom-format dump. `pg_restore --no-owner --no-acl` does
  not grant the application role access, so the drill grants `AUX_DB_USER` on
  the staging database before starting the server.
- `server-secrets.tar` from the bundle has `secrets.env` at its root. Extract it
  into the staging `server_secrets` volume, owned by `10001:10001` (the server
  image's `instant` user), and never leave a copy in `/tmp`.
- Restored `$files` rows refer to production object keys. Either copy those
  objects into the staging bucket or temporarily point staging at a read-only
  production files token. Revert the setting before the next staging deploy.
- **Destroy the production data and keysets afterwards.** Staging is disposable;
  a restore drill must not turn it into a long-lived copy of production. Drop the
  `aux-db` and `server_secrets` volumes and recreate them with the one-time
  staging setup.

## (b) The lifeboat

The lifeboat runs the same signed server digest against a restored or
point-in-time database, with the original `server_secrets`. Use
[`lifeboat/README.md`](lifeboat/README.md). The three failure modes to watch for:

- A new keyset generated by the platform instead of the restored one. OAuth
  secrets and BYOP connection strings become unreadable; check a stored OAuth
  app sign-in before declaring success.
- A database copy at the wrong time. Record the restore target (bundle
  `completedAt` or the PITR timestamp) next to the measured recovery time.
- A lifeboat left running after the drill. Destroy the app, the volume and the
  database copy; rotate any provider token created for it.

## (c) One app from its per-app backup

Per-app backups are zip archives written by the nightly worker or by **Create
backup** in the dashboard **Backups** tab. Restoring one creates a new app, so
this drill also checks tenant isolation: the original app and its neighbours must
keep serving throughout.

```sh
# Start the restore. The server chooses a new app id and returns it in the job.
curl -fsS -X POST \
  "https://api.<domain>/dash/restores/zip?title=Restore+drill" \
  -H "Authorization: Bearer $INSTANT_DASHBOARD_TOKEN" \
  -H 'Content-Type: application/zip' \
  --data-binary @instant-backup-<stamp>.zip

# Poll until job_status is done. An error keeps its message on the job row.
curl -fsS "https://api.<domain>/dash/restore-jobs/<job-id>" \
  -H "Authorization: Bearer $INSTANT_DASHBOARD_TOKEN"
```

The archive is restored in its canonical order (`config.json`, entity shards,
then storage blobs), so the files belong to the restored app and not to the
source app. Verify a file download and a query in the restored app, then confirm
a canary query in every other app still succeeds. Delete the restored app when
the drill is recorded; the source app and its backup are untouched.

## Record the result

`record-drill.sh` writes an append-only TSV ledger and prints one Markdown row.
It never reads Docker, the network or a secret.

```sh
sudo bash self-hosting/drills/record-drill.sh \
  --drill a \
  --date 2026-11-02 \
  --seconds 1840 \
  --notes "bundle 20261101T023000Z; apps/files/auth verified"
```

The default ledger is `/var/lib/backendrelay/drills/recovery-drills.tsv`; use
`sudo` like the backup tooling, or pass a writable `--ledger` path. Use
`--status failed` for a run that did not complete and keep the notes factual.
Copy the printed row into the table in
[`docs/operations.md#disaster-recovery-drills`](../../docs/operations.md#disaster-recovery-drills),
replacing the `pending` row for that drill.

`docs/operations.md` is the evidence the launch gate reads; the local ledger is
the backup for that row. Keep both until the next drill.

## Owner actions

In order, once the staging project and the lifeboat accounts exist:

1. Run the recorder once with `--ledger /tmp/drills-check.tsv` and delete the
   file, to confirm the command works on the host.
2. Decide and write down the target for each drill.
3. Run drill (a) and record the result. Destroy the production copy in staging.
4. Create the lifeboat account, test hostname and database copy, give the
   provider read access to the signed image, then run drill (b). Record it and
   tear the lifeboat down.
5. Run drill (c) against a non-critical app, record it, and delete the restored
   app.
6. Copy the three rows into `docs/operations.md` and check them at the next
   launch-gate review. Repeat (a) and (b) quarterly, (c) monthly, and all three
   after backup-tooling changes.
